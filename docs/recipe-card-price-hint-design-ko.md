# 설계: 저장한 레시피를 실제로 해먹게 만드는 MVP

생성일: 2026-05-20  
브랜치: main  
상태: DRAFT  
모드: Startup / 실패해도 사이드 프로젝트 가치가 남는 방향

현재 제품 형태 결정:

- 1단계는 모바일에서 쓰기 좋은 웹 MVP로 시작한다.
- 웹 MVP는 링크 붙여넣기, 레시피 카드화, 저장 레시피 추천, 가격 힌트를 검증하는 첫 제품이다.
- Supabase 백엔드는 처음부터 웹과 앱이 함께 쓸 수 있게 설계한다.
- 코드베이스는 pnpm workspace + Turborepo 기반 monorepo로 시작한다.
- Expo 네이티브 앱은 웹 MVP에서 반복 사용이 확인된 뒤 2단계로 만든다.
- 웹과 앱을 동시에 완성하려 하지 않는다.

## 문제 정의

요리를 자주 해먹는 1인가구는 유튜브, 블로그, 메모장, 카카오톡 나에게 보내기 등에 레시피 링크를 저장해둔다. 하지만 실제로 요리할 때는 다시 메모장을 열고, 링크를 누르고, 유튜브 설명란이나 페이지 본문을 다시 확인해야 한다.

현재 확인된 가장 강한 불편은 "레시피 링크를 저장해두지만, 요리할 때마다 원본 링크를 다시 열어야 해서 번거롭다"는 점이다.

초기 제품은 레시피 링크를 깔끔한 요리 카드로 바꾸는 것에서 시작하지만, 제품의 약속은 "저장"이 아니다. 핵심 약속은 사용자가 저장해둔 레시피 중 지금 해먹기 좋은 메뉴를 고르게 해주는 것이다.

재료 가격 기능은 첫 버전에서 정교한 최저가 비교나 정확한 총 재료비 계산이 아니다. 주요 재료 가격을 바탕으로 "최근보다 저렴한 편", "보통 가격대", "가격 정보 부족" 같은 가격 힌트를 제공한다.

## 수요 증거

현재 확인된 증거:

- 대상 사용자 예시: 배달보다 직접 요리를 더 자주 해먹는 자취생.
- 현재 행동: 유튜브 레시피 링크를 메모장에 저장한다.
- 저장 규모: 메모장에 약 10개 정도의 레시피 링크가 있다.
- 실제 예시: 제육볶음 레시피.
- 표현된 불편: 요리할 때마다 저장된 링크를 다시 열어 확인해야 해서 번거롭다.

아직 검증되지 않은 가설:

- 사용자가 재료 시세를 보고 메뉴 선택을 바꿀지.
- 사용자가 레시피 저장 또는 가격 힌트에 돈을 낼지.
- 사용자가 남는 재료 관리 기능을 꾸준히 입력하고 사용할지.

## 현재 대안

현재 사용자는 대략 이런 흐름을 가진다.

1. 유튜브에서 레시피를 찾는다.
2. 링크를 메모장에 저장한다.
3. 요리할 때 메모장을 연다.
4. 저장된 유튜브 링크를 누른다.
5. 설명란이나 영상을 다시 보면서 재료와 순서를 확인한다.

이 서비스가 만들고 싶은 흐름은 더 짧다.

1. 요리하려고 한다.
2. 레시피 웹앱을 연다.
3. 저장된 레시피 카드에서 바로 재료와 순서를 본다.

핵심은 "링크 저장 앱"이 아니라 "오늘 뭐 해먹을지 고를 때 먼저 여는 서비스"가 되는 것이다.

## 첫 타깃 사용자

초기 타깃은 넓은 의미의 1인가구가 아니다.

초기 타깃:

- 한국의 자취생 또는 사회초년생.
- 배달보다 직접 해먹는 빈도가 높은 사람.
- 유튜브나 블로그 레시피를 자주 참고하는 사람.
- 레시피 링크를 메모장, 카톡, 유튜브 저장목록, 북마크 등에 저장해둔 사람.
- 저장한 레시피를 반복해서 다시 열어보는 사람.

이 타깃은 "요리 초보 전체"보다 좁지만, 첫 제품 검증에는 더 좋다. 이미 저장 행동이 있기 때문에 새 서비스가 대체할 대상이 분명하다.

## 가장 작은 쐐기

첫 MVP의 쐐기는 다음 한 문장이다.

> 내가 저장한 레시피 중 오늘 또는 이번 주에 해먹기 좋은 메뉴를 바로 고르게 해준다.

첫 버전에서 사용자가 얻는 가치는:

- 더 이상 메모장 안의 링크를 뒤지지 않아도 된다.
- 유튜브 설명란을 매번 다시 확인하지 않아도 된다.
- 내가 저장한 레시피들이 한 곳에 모인다.
- 주요 재료의 가격 힌트를 보고 어떤 저장 레시피를 먼저 해먹을지 고를 수 있다.

## 전제

1. 첫 MVP는 전체 meal planning 앱이 아니라 "저장한 레시피를 실제로 해먹게 만드는 모바일 웹 서비스"이다.
2. 현재 가장 강한 수요 증거는 가격 최적화가 아니라 링크를 요리 카드로 바꾸는 편의성이다.
3. 가격 기능은 첫 버전에서 정교한 최저가 비교가 아니라 메뉴 선택을 돕는 가벼운 힌트로 제공한다.
4. 첫 사용자는 "1인가구 전체"가 아니라 "요리를 자주 하고 유튜브 레시피 링크를 저장해두는 사람"이다.
5. 성공 기준은 파싱 성공률이 아니라, 사용자가 메뉴를 고르거나 실제 요리할 때 다시 앱을 여는지다.

## 검토한 접근안

### 접근안 A: 링크 → 레시피 카드 MVP

사용자가 유튜브 또는 웹 레시피 링크를 붙여넣으면, 웹앱이 제목, 썸네일, 재료, 조리 순서, 원본 링크를 저장한다. 주요 재료 2-3개에 대해서만 가격 힌트를 붙인다.

노력: S/M  
위험: 낮음-중간

장점:

- 지금 확인된 불편과 가장 직접적으로 연결된다.
- MVP를 작게 만들 수 있다.
- 가격 기능을 완전히 버리지 않으면서도 초기 복잡도를 낮춘다.

단점:

- 단순 레시피 저장소처럼 보이면 기존 앱과 차이가 약하다.
- 가격 힌트가 너무 약하면 "합리적 소비" 메시지가 흐려질 수 있다.
- 사용자가 충분히 많은 레시피를 저장하지 않으면 재방문 이유가 약하다.

### 접근안 B: 이번 주 해먹기 좋은 메뉴 추천

저장된 레시피 중 현재 주요 재료 가격이 괜찮은 메뉴를 추천한다. 레시피 저장은 추천을 위한 입력 수단이 된다.

노력: M/L  
위험: 중간-높음

장점:

- 기존 레시피 저장 앱보다 차별점이 선명하다.
- "오늘 뭐 해먹지?"라는 반복적인 결정 순간에 들어갈 수 있다.
- 가격 데이터가 제품의 중심 가치가 된다.

단점:

- 쿠팡 상품 매칭 정확도가 낮으면 신뢰가 깨진다.
- 저장된 레시피가 적으면 추천 품질이 낮다.
- 첫 버전부터 가격 점수, 랭킹, 추천 이유를 설계해야 한다.

### 접근안 C: 가격 없는 초간단 레시피 저장함

가격 기능을 빼고, 링크 붙여넣기, 레시피 추출, 검색, 요리 모드만 만든다.

노력: S  
위험: 낮음

장점:

- 가장 빨리 만들 수 있다.
- 사이드 프로젝트로 실패해도 개인적으로 쓸 수 있다.
- 파싱 품질과 요리 중 사용성에 집중할 수 있다.

단점:

- 사업적 차별점이 가장 약하다.
- 가격 기반 합리적 소비라는 원래 비전이 뒤로 밀린다.
- 유료화 근거를 만들기 어렵다.

## 추천 접근

접근안 A를 선택하되, 제품 프레이밍은 한 단계 올린다.

첫 제품은 "링크를 붙여넣으면 바로 요리 가능한 레시피 카드가 생긴다"는 경험을 기반으로 한다. 하지만 첫 화면과 제품 메시지는 "레시피 저장소"가 아니라 "이번 주 해먹기 좋은 저장 레시피"가 되어야 한다.

즉 구현 범위는 작게 유지하되, 사용자가 웹앱을 다시 여는 이유를 더 강하게 만든다.

- 링크 붙여넣기: 레시피 카드를 만들기 위한 입력 수단.
- 레시피 카드: 요리할 때 보는 실행 화면.
- 가격 힌트: 어떤 저장 레시피를 먼저 해먹을지 고르는 판단 신호.

가격 표현은 정확한 총액보다 신뢰를 우선한다.

좋은 표현:

- 주요 재료 예상가
- 최근보다 저렴한 편
- 보통 가격대
- 가격 정보 부족
- 상품 매칭 확인 필요

피해야 할 표현:

- 제육볶음 총 재료비 8,732원
- 오늘이 최저가
- 지금 반드시 해먹기 좋은 시기

정확해 보이는 숫자가 틀리면 신뢰가 바로 깨진다. 첫 버전에서는 "정확한 가격 계산기"보다 "요리 결정에 도움 되는 힌트"가 맞다.

## MVP 범위

포함:

- 모바일 웹앱 기준의 첫 제품.
- 로그인.
- 레시피 링크 붙여넣기.
- 유튜브 링크와 일반 웹 링크 구분.
- 유튜브는 제목, 썸네일, 설명란을 우선 활용.
- 일반 웹 페이지는 본문을 추출한 뒤 LLM으로 재료와 조리법 파싱.
- 저장 전 확인 화면 제공.
- 사용자가 재료와 조리 순서를 수정할 수 있게 함.
- 저장된 레시피 목록.
- 레시피 검색.
- 홈 화면의 "이번 주 해먹기 좋은 저장 레시피" 영역.
- 각 추천 카드의 짧은 이유: 예) "돼지고기 가격이 최근보다 낮은 편".
- 요리할 때 보기 좋은 레시피 카드 화면.
- 주요 재료 2-3개에 대한 가격 힌트.
- 원본 링크 보존.

제외:

- Expo 네이티브 앱 전체 구현.
- 앱스토어/플레이스토어 출시.
- push notification.
- 모바일 공유 시트.
- 냉장고 재료 관리.
- 남은 재료 유통기한 알림.
- 자동 장보기 리스트.
- 주간 식단표.
- 정확한 전체 재료비 계산.
- 영양성분 분석.
- 소셜 공유.
- 가족/공동 계정.

## 사용자 흐름

1. 사용자가 유튜브 또는 레시피 페이지 URL을 붙여넣는다.
2. 웹앱이 소스 정보를 가져온다.
3. 웹앱이 제목, 썸네일, 재료, 조리 순서를 추출한다.
4. 웹앱이 저장 전 확인 화면을 보여준다.
5. 사용자가 잘못된 재료나 순서를 수정한다.
6. 사용자가 레시피 카드를 저장한다.
7. 홈 화면에서 "이번 주 해먹기 좋은 저장 레시피"를 본다.
8. 사용자는 추천 이유를 보고 메뉴를 고른다.
9. 요리할 때는 원본 링크 대신 카드 화면을 본다.
10. 카드 안에서 주요 재료 가격 힌트와 원본 링크를 확인할 수 있다.

## 성공 기준

첫 검증 목표:

- 실제 타깃 사용자 5명을 모집한다.
- 각 사용자가 본인이 이미 저장해둔 레시피 링크 5개 이상을 가져온다.
- 5명 중 3명 이상이 일주일 안에 메뉴를 고르거나 요리할 때 웹앱을 다시 연다.
- 5명 중 3명 이상이 기존 메모장/유튜브 저장목록보다 편하다고 말한다.
- 5명 중 2명 이상이 가격 힌트나 추천 이유를 보고 메뉴 선택에 도움을 받았다고 말한다.

이 기준을 통과하기 전에는 냉장고 관리, 장보기 리스트, 정교한 메뉴 추천으로 확장하지 않는다.

## 배포 계획

첫 버전은 모바일 웹앱으로 시작한다. 기술적으로는 Next.js 웹 MVP와 Supabase 백엔드를 기준으로 한다.

Repository 구조는 monorepo로 시작한다.

- `apps/web`: Next.js 웹 MVP.
- `apps/mobile`: Expo 앱이 검증 후 들어올 자리. 1단계에서는 만들지 않는다.
- `packages/shared`: 웹과 앱이 공유할 타입, validation, 추천 점수 로직.
- `packages/config`: TypeScript/ESLint 같은 공통 설정.
- `supabase`: migration과 Edge Functions.

이유:

- 사용자는 유튜브, 카톡, 메모장에서 링크를 복사해 바로 붙여넣을 수 있다.
- 앱스토어 심사 없이 빠르게 수정할 수 있다.
- 네이티브 앱보다 검증 속도가 빠르다.
- Supabase 백엔드를 공용으로 만들면 나중에 Expo 앱을 붙일 때 데이터를 다시 설계하지 않아도 된다.
- monorepo로 시작하면 Expo 앱을 추가할 때 타입, validation, 추천 로직을 복사하지 않아도 된다.

초기 배포:

- 테스트 사용자 5-10명에게 직접 링크 공유.
- 사용자가 실제 저장해둔 레시피 링크를 가져오게 함.
- 사용자가 링크를 붙여넣고 카드가 생기는 과정을 관찰.
- 홈 화면의 "이번 주 해먹기 좋은 저장 레시피"에서 어떤 메뉴를 고르는지 관찰.

검증 이후:

- PWA 설치 지원.
- 반복 사용이 확인된 뒤 Expo 앱 시작.
- Expo 앱에서는 저장 레시피 재방문, 요리 중 보기 좋은 화면, 이후 push notification과 공유 시트를 강화.
- 브라우저 확장은 Expo 앱 이후에도 필요성이 확인될 때만 검토.

Expo 앱 전환 기준:

- 5명 이상이 각자 실제 저장 레시피 5개 이상을 넣었다.
- 3명 이상이 7일 안에 다시 들어와 추천 또는 저장 레시피를 확인했다.
- 2명 이상이 가격 힌트 또는 추천 이유가 메뉴 선택에 도움이 됐다고 말했다.
- 웹에서 링크 붙여넣기, 파싱 결과 확인, 저장 흐름이 큰 설명 없이 작동했다.
- "앱이면 더 자주 쓸 것 같다"는 피드백이 2명 이상에게서 나왔다.

## 외부 의존성

구현 전에 확인해야 할 것:

- YouTube Data API로 설명란과 메타데이터를 안정적으로 가져올 수 있는지.
- YouTube API quota가 초기 사용량을 감당하는지.
- 한국어 레시피 페이지와 유튜브 설명란에서 LLM 파싱 품질이 충분한지.
- 쿠팡 API 사용 조건이 가격 표시와 추적 기능을 허용하는지.
- "돼지고기 앞다리살", "양파", "고추장" 같은 재료명이 쿠팡 상품과 얼마나 정확히 매칭되는지.
- 가격 힌트를 어떤 단위로 보여줄지: 현재가, 단위 가격, 최근 대비 저렴/보통/비쌈.

- 쿠팡 API 정책상 가격 표시와 추적이 가능한가?
- 사용자는 파싱 결과를 직접 수정할 의향이 있는가?
- 가격 힌트는 어느 정도로 정확해야 신뢰를 얻는가?
- 어떤 추천 이유가 사용자의 메뉴 선택을 실제로 바꾸는가?
- 유료화는 저장 개수 제한, 가격 힌트, 추천 기능 중 어디에 붙일 수 있는가?

## 다음 과제

가능하면 코드를 작성하기 전에 5명에게 수동 검증을 한다. 현실적으로 어렵다면 웹 MVP의 첫 사용자 테스트를 아래 절차와 같은 기준으로 진행한다.

각 사용자에게 다음을 요청한다.

1. 현재 레시피 링크를 어디에 저장하는지 보여달라고 한다.
2. 실제 저장해둔 링크 5개를 보내달라고 한다.
3. 그 링크를 수동으로 레시피 카드 형태로 정리한다.
4. 주요 재료 2-3개에 대해 대략적인 가격 힌트를 붙인다.
5. 사용자의 저장 레시피 중 "이번 주 해먹기 좋은 메뉴" 2-3개를 골라 추천 이유를 적는다.
6. 정리된 카드를 다시 보내고, 일주일 안에 메뉴를 고르거나 실제 요리할 때 써보게 한다.
7. 사용자가 다시 카드를 열어보는지 확인한다.

핵심 질문은 하나다.

> 사용자가 리마인드 없이도 메뉴를 고르거나 요리할 때 이 카드를 다시 여는가?

## 관찰한 점

- 처음에는 "1인가구"라고 넓게 잡았지만, 대화 중 "유튜브 레시피 링크를 메모장에 10개 정도 저장해둔 자취생"으로 좁혀졌다. 이 좁힘이 중요하다.
- "요리를 한다 → 해당 서비스를 들어가서 내가 저장해둔 레시피를 보고 요리한다"는 표현이 제품의 핵심 UX를 잘 설명한다.
- 가격 비교, 남는 재료 처리, 재료 손실 방지까지 확장하고 싶은 욕심이 보인다. 좋은 방향이지만 첫 버전에서는 위험하다.
- 이 제품의 핵심은 "AI가 레시피를 파싱한다"가 아니다. 핵심은 "저장한 레시피를 실제로 해먹게 한다"이다.
